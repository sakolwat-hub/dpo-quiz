1️⃣ ฐานทางกฎหมาย (Lawful Basis) — ออก 8 ข้อ

📚 มาตราหลัก: ม.24 (ข้อมูลทั่วไป 7 ฐาน) + ม.26 (Sensitive 5 ข้อยกเว้น)

🎯 ม.24 — 7 ฐาน (ข้อมูลทั่วไป):
ฐานใช้เมื่อตัวอย่าง
ม.24(1) Consentไม่มีฐานอื่นใช้ได้ส่ง Marketing คนใหม่, Sensitive Marketing
ม.24(2) Vitalป้องกันชีวิต/สุขภาพ เจ้าของให้ Consent ไม่ได้ผู้ป่วยหมดสติ, อุบัติเหตุ
ม.24(3) Contractจำเป็นต่อสัญญา + Pre-contractสมัครงาน CV, ส่งของตามออเดอร์, จ้างงาน
ม.24(4) Public Taskภารกิจของรัฐทะเบียนราษฎร, ตำรวจสืบคดี
ม.24(5) LIประโยชน์โดยชอบ + LIA + ไม่กระทบสิทธิเกินควรCCTV ความปลอดภัย, IT Security, Marketing ลูกค้าเก่า
ม.24(6) Legal Obligationกฎหมายบังคับภาษี, ประกันสังคม, AML/ปปง., รายงาน อย.
ม.24(7) Public Interest/Researchวิจัย-สถิติตามจริยธรรมวิจัยทางการแพทย์/สังคม
🎯 ม.26 — Sensitive Data (ความยินยอมโดยชัดแจ้ง + 5 ข้อยกเว้น):
ฐานใช้เมื่อ
ม.26 วรรค 1Explicit Consent — เป็นค่าตั้งต้น
ม.26(1) Vitalป้องกันชีวิตเมื่อให้ Consent ไม่ได้ (ผู้ป่วยหมดสติ)
ม.26(2) ภารกิจไม่แสวงกำไรมูลนิธิ-สมาคม ใช้ของสมาชิก
ม.26(3) เปิดเผยต่อสาธารณะโดยเจ้าของเองเจ้าของโพสต์เอง
ม.26(4) คดีความ-สิทธิเรียกร้องฟ้องคดี/ต่อสู้คดี
ม.26(5)(ก) อาชีวเวชศาสตร์/รักษาตรวจสุขภาพประจำปี, รักษาผู้ป่วย
ม.26(5)(ข) สาธารณสุขป้องกันโรคระบาด
ม.26(5)(ค) Labor Law/SocSecประกันสังคม, แรงงาน, สวัสดิการ
ม.26(5)(ง) วิจัยทางวิทย์มี IRB
ม.26(5)(จ) ประโยชน์สาธารณะที่สำคัญตามกฎหมาย
⚠️ Sensitive Data ตาม ม.26: เชื้อชาติ · ศาสนา · ความเชื่อ · พฤติกรรมทางเพศ · ประวัติอาชญากรรม · สุขภาพ · ความพิการ · สหภาพ · พันธุกรรม · Biometric (ลายนิ้วมือ-Face ID) · ความเห็นทางการเมือง

🚨 Trap Cards:
  • "Marketing ลูกค้าเก่า" = LI ม.24(5) ได้ แต่ ต้องให้ Opt-out ฟรี
  • "Marketing ลูกค้าใหม่" = ต้อง Consent ม.24(1)
  • "CCTV ลานจอด/ทางเข้า" = LI ม.24(5) + ติดป้ายแจ้ง
  • "พนักงานหักภาษี" = Legal Obligation ม.24(6) ไม่ใช่ Contract
  • "ผู้ป่วยหมดสติ" = Vital ม.26(1) ไม่ใช่ ม.24(2) ถ้าเป็นข้อมูลสุขภาพ
  • "Biometric เข้างาน" = Sensitive ต้อง Explicit Consent หรือ ม.26(5)(ค)
  • "KYC ประวัติคดี" = Sensitive ต้อง Explicit Consent

2️⃣ สิทธิเจ้าของข้อมูล (DSR) ม.30-36 — ออก 6 ข้อ

มาตราสิทธิคำลวง / Trick
ม.30Right to Access + ขอสำเนาตอบใน 30 วัน · ขยายได้ 30 วัน · ปฏิเสธต้องให้เหตุผล
ม.31Right to Data Portabilityเฉพาะ Consent / Contract · รูปแบบ Machine-Readable
ม.32Right to Object (คัดค้าน)คัดค้าน LI / Direct Marketing / Public Task / วิจัย
ม.33Right to Erasure (ลบ)ลบเมื่อหมดความจำเป็น/ถอน Consent · ปฏิเสธได้ถ้ายังต้องเก็บตามกฎหมาย
ม.34Right to Restriction (ระงับ)ระงับชั่วคราว เช่น ระหว่างตรวจสอบความถูกต้อง
ม.35Right to Rectification (แก้ไข)ทำให้ถูกต้อง-เป็นปัจจุบัน-สมบูรณ์
ม.36หน้าที่ Controllerแจ้งบุคคลที่สาม-ผู้รับโอนเมื่อมีการแก้/ลบ
📌 ตัวเลขทอง DSR: 30 วัน + ขยาย 30 วัน · ฟรี (เว้นแต่ขอซ้ำ/เกินเหตุ)

⚠️ ม.19 — Withdraw Consent: เพิกถอนได้ทุกเวลา · ง่ายเหมือนตอนให้ · ไม่กระทบการประมวลผลที่ทำไปแล้วโดยชอบ

🚨 Trap Cards:
  • Portability ใช้ได้ เฉพาะ Consent/Contract เท่านั้น (ไม่ใช่ทุกฐาน)
  • Erasure ปฏิเสธได้ถ้ามี Legal Obligation/Public Task/วัตถุประสงค์ยังจำเป็น
  • เด็ก <10 ปี ขอ Consent ผู้แทนโดยชอบธรรม เท่านั้น (ม.20)
  • เด็ก 10-20 ปี ขอเอง + ผู้แทน ในเรื่องสำคัญ

3️⃣ ประกาศ กคส. มาตรการความมั่นคงปลอดภัย พ.ศ.2565 — ออก 9 ข้อ

📚 ฐาน: ออกตาม ม.37(1) — Controller ต้องจัดให้มีมาตรการรักษาความมั่นคงปลอดภัย

🎯 3 ประเภทมาตรการ (CIA Triad):
ประเภทตัวอย่าง
Organizational Measure (เชิงองค์กร)นโยบาย · Compliance Audit · Awareness Training · DPO · DPA · ROPA · Privacy Notice · Incident Response Plan
Technical Measure (เชิงเทคนิค)Encryption · MFA · Access Control · Firewall · Anti-virus · Backup · DLP · SIEM · Logging · Pseudonymization
Physical Measure (เชิงกายภาพ)กุญแจ · CCTV · เก็บเอกสารในตู้เซฟ · Access Card เข้าห้อง Server · ทำลายเอกสารแบบ Shred
🎯 หลักการ CIA Triad:
  • Confidentiality = ความลับ (รั่ว = อีเมลผิดคน)
  • Integrity = ความถูกต้อง (แก้ไขโดยมิชอบ)
  • Availability = ความพร้อมใช้ (DDoS, Ransomware, ไฟไหม้)
🎯 องค์ประกอบของมาตรการตามประกาศ:
  1. ทบทวนความเสี่ยง (Risk Assessment)
  2. มาตรการต้องเหมาะกับ ประเภท ปริมาณ ความเสี่ยง
  3. การควบคุมการเข้าถึง (Access Control) — Identification → Authentication → Authorization
  4. การกำหนด หน้าที่และความรับผิดชอบ
  5. การ ทบทวน/ปรับปรุง มาตรการอย่างสม่ำเสมอ
  6. การสร้างความตระหนัก (Awareness)
🚨 Trap Cards:
  • "Compliance Audit" = Organizational Measure (ไม่ใช่ Technical)
  • "Awareness Training" = Organizational
  • "Encryption / MFA / Anti-virus" = Technical
  • "กุญแจ / CCTV / Access Card" = Physical
  • ต้องคำนึงถึง "ความเสี่ยงที่อาจเกิดต่อสิทธิเสรีภาพ" ของเจ้าของข้อมูล

4️⃣ ประกาศ กคส. แจ้งเหตุละเมิด พ.ศ.2565 — ออก 10 ข้อ (เยอะที่สุด)

📚 ฐาน: ม.37(4) — แจ้ง สำนักงาน กคส. ภายใน 72 ชั่วโมง นับแต่ ทราบเหตุ (Aware) — ยกเว้นไม่เสี่ยงต่อสิทธิเสรีภาพ

🎯 ตัวเลขทอง:
  • 72 ชั่วโมง — แจ้ง PDPC นับแต่ "ทราบเหตุ" (ไม่ใช่ตั้งแต่เกิดเหตุ)
  • 15 วัน — เกิน 72 ชม. ต้องส่งเหตุผลล่าช้า
  • เสี่ยงสูง = แจ้งทั้ง PDPC + เจ้าของข้อมูล โดยไม่ชักช้า
🎯 3 ระดับเหตุละเมิด:
ระดับเกณฑ์การแจ้ง
ไม่เสี่ยงไม่กระทบสิทธิเสรีภาพไม่ต้องแจ้ง แต่ต้องบันทึก
เสี่ยงกระทบสิทธิแจ้ง PDPC ภายใน 72 ชม.
เสี่ยงสูงเสี่ยงต่อสิทธิเสรีภาพอย่างมากแจ้ง PDPC + เจ้าของข้อมูล
🎯 เนื้อหาการแจ้ง PDPC ต้องมี:
  1. ลักษณะ + ประเภท + ปริมาณ ของข้อมูลที่ละเมิด
  2. ผลกระทบที่อาจเกิดขึ้น
  3. มาตรการเยียวยา-ลดความเสียหาย
  4. ผู้ติดต่อ (DPO) + ช่องทาง
🎯 ขั้นตอนรับมือ Breach (IRP):
  1. Detect (ตรวจพบ)
  2. Contain (จำกัดความเสียหาย)
  3. Assess Risk (ประเมินความเสี่ยงต่อสิทธิเสรีภาพ)
  4. Notify (PDPC ภายใน 72 ชม. / เจ้าของข้อมูลถ้าเสี่ยงสูง)
  5. Remediate + Lessons Learned
🎯 ตัวอย่างเหตุละเมิด:
  • อีเมลส่งผิดคน (Confidentiality)
  • โน๊ตบุ๊กหายที่ยังไม่เข้ารหัส (Confidentiality)
  • Ransomware เข้ารหัสข้อมูล (Availability + อาจ Confidentiality)
  • Phishing ทำให้ Account หลุด (Confidentiality)
  • พนักงานเปิดเผยโดยมิชอบ (Confidentiality)
  • Database ถูกแก้ไขโดยไม่ได้รับอนุญาต (Integrity)
🚨 Trap Cards:
  • 72 ชม. นับจาก "ทราบเหตุ" (Aware) ไม่ใช่ "เกิดเหตุ"
  • หาก Processor พบเหตุ → แจ้ง Controller โดยไม่ชักช้า (Controller เป็นผู้แจ้ง PDPC)
  • เครื่องหายแต่ Encrypted ครบ → อาจ ไม่ต้องแจ้ง เจ้าของข้อมูล
  • ไม่แจ้ง = โทษทางปกครอง ปรับสูงสุด 3 ล้าน (ม.83(2))
  • การแจ้งเจ้าของข้อมูล ต้องใช้ ภาษาเข้าใจง่าย (Plain Language)

5️⃣ ส่ง/โอนข้อมูลไปต่างประเทศ ม.28-29 + ประกาศ 2566 — ออก 5 ข้อ

📚 ม.28: ปลายทางต้องมีมาตรฐาน คุ้มครองเพียงพอ (Adequacy) ตาม PDPC ประกาศ
📚 ม.29: หากไม่ Adequacy ต้องใช้ มาตรการคุ้มครองที่เพียงพอและบังคับใช้ได้จริง

🎯 ข้อยกเว้น ม.28 (ส่งได้แม้ไม่ Adequacy):
  1. ปฏิบัติตาม กฎหมาย
  2. ได้รับ Consent โดยแจ้งความเสี่ยง (Informed Consent)
  3. จำเป็นต่อ สัญญา ที่เจ้าของข้อมูลเป็นคู่สัญญา/ขอก่อนทำสัญญา
  4. จำเป็นต่อสัญญา เพื่อประโยชน์เจ้าของข้อมูล
  5. ป้องกัน อันตรายต่อชีวิต/ร่างกาย/สุขภาพ เจ้าของข้อมูลให้ Consent ไม่ได้
  6. ประโยชน์สาธารณะ ที่สำคัญ
🎯 มาตรการคุ้มครอง ม.29 (ทางเลือก):
เครื่องมือใช้เมื่อ
BCRs (Binding Corporate Rules)โอนภายใน เครือบริษัท ข้ามชาติ · PDPC อนุมัติ
SCCs (Standard Contractual Clauses)สัญญามาตรฐานที่ PDPC กำหนดหรือยอมรับ
ข้อกำหนดของ Code of Conduct / Certificationที่ PDPC รับรอง
กลไกอื่นที่ PDPC ยอมรับ
🎯 ประกาศ 2566 (ม.28):
  • กำหนดเกณฑ์ "Adequacy" ที่ PDPC จะใช้พิจารณา
  • พิจารณา: หลักนิติธรรม · หน่วยงานกำกับ · สิทธิเจ้าของข้อมูล · กลไกบังคับใช้
🎯 ประกาศ 2566 (ม.29):
  • กำหนดรูปแบบ BCRs / SCCs
  • BCRs ต้องผ่าน การรับรองจาก PDPC
  • SCCs ต้องครอบคลุม: บทบาท Controller-Processor · สิทธิเจ้าของข้อมูล · ความรับผิด · กลไกระงับข้อพิพาท
🚨 Trap Cards:
  • ม.28 = Adequacy / ม.29 = มาตรการคุ้มครองอื่น (BCRs/SCCs)
  • "กลุ่มบริษัทเดียวกัน" → ใช้ BCRs
  • "คู่ค้าต่างประเทศ" → ใช้ SCCs
  • Cloud Service (AWS/GCP/Azure) → ดู Region + DPA + SCCs

6️⃣ กลไกบังคับใช้กฎหมาย — ออก 3 ข้อ

🎯 3 โทษ:
ประเภทตัวเลขมาตรา
โทษอาญาจำคุกไม่เกิน 1 ปี ปรับไม่เกิน 1 ล้าน หรือทั้งจำทั้งปรับ (Sensitive: 6 เดือน-1 ปี)ม.79-81
โทษทางปกครองปรับสูงสุด 1 / 3 / 5 ล้านบาทม.82-87
โทษทางแพ่งค่าสินไหม + Punitive สูงสุด 2 เท่าม.77-78
🎯 หน่วยงานกำกับ:
  • คณะกรรมการคุ้มครองข้อมูลส่วนบุคคล (กคส.) — ออกประกาศ + พิจารณาอุทธรณ์
  • คณะกรรมการผู้เชี่ยวชาญ (Specialist Committee) — รับเรื่องร้องเรียน + สั่งปรับ
  • สำนักงาน กคส. (PDPC Office) — งานสนับสนุน + รับแจ้งเหตุ Breach
🎯 กระบวนการร้องเรียน:
  1. ผู้เสียหายร้องต่อ คณะกรรมการผู้เชี่ยวชาญ
  2. คณะกรรมการสอบสวน → สั่งระงับ/แก้ไข/ปรับ
  3. อุทธรณ์ต่อ กคส. ภายใน 30 วัน
  4. ฟ้องศาลปกครอง
🎯 โทษเฉพาะ Sensitive Data:
  • ใช้ Sensitive โดยไม่ Consent → ปรับสูงสุด 5 ล้าน + อาจ จำคุก
  • ส่ง Sensitive ออกนอกประเทศโดยไม่เป็นไปตาม ม.28-29 → ปรับสูงสุด 5 ล้าน
🚨 Trap Cards:
  • ผู้บริหารรับผิด ร่วม ตาม ม.81 หากปล่อยปละ
  • หากร่วมมือกับ PDPC → บรรเทาโทษ ได้
  • โทษอาญาต้อง ทำให้ผู้อื่นเสียหายโดยรู้ หรือ เสียหายต่อชื่อเสียง

7️⃣ หลักการพื้นฐาน (Principles) — ออก 1 ข้อ

🎯 7 หลักการ GDPR/PDPA (ต้องท่อง):
  1. Lawfulness, Fairness, Transparency — ชอบด้วยกฎหมาย/เป็นธรรม/โปร่งใส
  2. Purpose Limitation — ใช้ตามวัตถุประสงค์ที่แจ้ง
  3. Data Minimization — เก็บเท่าที่จำเป็น
  4. Accuracy — ถูกต้อง-เป็นปัจจุบัน
  5. Storage Limitation — ไม่เก็บนานเกินจำเป็น
  6. Integrity & Confidentiality (Security) — มั่นคงปลอดภัย
  7. Accountability — รับผิดชอบและพิสูจน์ได้
🎯 หลัก PbD (Privacy by Design) — 7 Principles ของ Cavoukian:
  1. Proactive not Reactive
  2. Privacy as Default Setting
  3. Privacy Embedded into Design
  4. Full Functionality (Win-Win)
  5. End-to-End Security
  6. Visibility & Transparency
  7. Respect for User Privacy
🚨 Trap Cards:
  • "เก็บเผื่อใช้ในอนาคต" = ผิด Purpose Limitation
  • "เก็บไว้ตลอดชีวิต" = ผิด Storage Limitation
  • "Pre-ticked Consent" = ผิด Lawfulness/Fairness

8️⃣ ประกาศ กคส. การลบ/ทำให้ไม่ระบุตัวตน พ.ศ.2567 — ออก 1 ข้อ

📚 ฐาน: ออกตาม ม.33 + ม.37 — Controller ต้องลบ/ทำลาย/ทำให้ไม่ระบุตัวตน

🎯 3 วิธี:
วิธีความหมายตัวอย่าง
ลบ (Delete)ลบออกจากระบบลบ record จาก DB
ทำลาย (Destroy)ทำลายสื่อบันทึกShred กระดาษ · Wipe HDD
Anonymizationทำให้ไม่ระบุตัวบุคคล โดยถาวรลบ ID + ตัดข้อมูลเฉพาะ
🎯 ความแตกต่าง:
  • Anonymization = กลับคืนไม่ได้ (Irreversible) → ออกจากขอบเขต PDPA
  • Pseudonymization = แทนด้วยรหัส แต่ กลับคืนได้ → ยังเป็น Personal Data
🎯 ปัจจัยที่ต้องคำนึง:
  1. ประเภท + ปริมาณ ของข้อมูล
  2. ความเสี่ยง
  3. เทคโนโลยีที่ใช้
  4. ค่าใช้จ่ายและความเหมาะสม
  5. ระยะเวลาเก็บตามกฎหมาย
🚨 Trap Cards:
  • "Pseudonymization" ≠ "Anonymization" — ยังต้องคุ้มครอง
  • Backup ลบไม่ได้ทันที → ใช้ Restriction + ลบในรอบ Backup ถัดไป
  • กฎหมายอื่นบังคับเก็บ (เช่น บัญชี 5-10 ปี) → ปฏิเสธการลบได้

9️⃣ ประเภทข้อมูล Sensitive ตาม ม.26 — ออก 1 ข้อ

🎯 11 ประเภท Sensitive Data:
  1. เชื้อชาติ (Race)
  2. เผ่าพันธุ์ (Ethnic Origin)
  3. ความคิดเห็นทางการเมือง (Political Opinion)
  4. ความเชื่อ ในลัทธิ ศาสนา หรือปรัชญา
  5. พฤติกรรมทางเพศ (Sexual Behaviour)
  6. ประวัติอาชญากรรม (Criminal Record)
  7. ข้อมูลสุขภาพ (Health Data)
  8. ความพิการ (Disability)
  9. ข้อมูล สหภาพแรงงาน (Trade Union)
  10. ข้อมูล พันธุกรรม (Genetic Data)
  11. ข้อมูล ชีวภาพ (Biometric) ที่ระบุตัวบุคคล
🎯 Biometric ที่เป็น Sensitive:
  • ลายนิ้วมือ · Face ID · ม่านตา · ลายฝ่ามือ · เสียง (เพื่อระบุตัว) · DNA
🚨 Trap Cards:
  • "เลขบัตรประชาชน" ≠ Sensitive (เป็น PII ทั่วไป)
  • "ลายเซ็น Digital" ≠ Sensitive (เว้นแต่ใช้ Biometric)
  • "ข้อมูลเด็ก" ≠ Sensitive ตาม ม.26 แต่ต้องระวังพิเศษ ม.20
  • "ความพิการ" = Sensitive (ข้อมูลสุขภาพ)

🔟 มาตรา 5 PDPA — ขอบเขตการบังคับใช้ — ออก 1 ข้อ

📚 หลัก: PDPA ใช้บังคับกับ Controller / Processor ใน 2 กรณี

🎯 ม.5 วรรค 1 — ในประเทศ:
  • Controller / Processor ที่อยู่ ในราชอาณาจักร ไม่ว่าจะประมวลผลในหรือนอกประเทศ
🎯 ม.5 วรรค 2 — นอกประเทศ (Extraterritorial):
  • Controller / Processor ที่อยู่ นอกราชอาณาจักร หากเป็น
    1. การ เสนอสินค้า/บริการ ให้เจ้าของข้อมูลในไทย (มี/ไม่มีเงิน)
    2. การ เฝ้าติดตามพฤติกรรม เจ้าของข้อมูลที่อยู่ในไทย
🎯 ข้อยกเว้น (ไม่บังคับใช้):
  • ใช้เพื่อ กิจการครอบครัวส่วนตัว
  • หน่วยงานรัฐ ด้านความมั่นคง / ป้องกันปราบปรามอาชญากรรม
  • สื่อมวลชน-ศิลปกรรม-วรรณกรรม ตาม จริยธรรมสื่อ
  • สภาผู้แทน-วุฒิสภา-รัฐสภา
  • การพิจารณาคดีของศาล
  • Credit Bureau
🚨 Trap Cards:
  • เว็บต่างประเทศที่ขายของให้คนไทย = เข้าข่าย PDPA
  • กิจการส่วนตัวในบ้าน = ไม่เข้าข่าย
  • Credit Bureau อยู่ภายใต้ กฎหมายเฉพาะ ไม่ใช่ PDPA

1️⃣1️⃣ มาตรา 4 PDPA — ข้อยกเว้นการบังคับใช้ — ออก 1 ข้อ

📚 หลัก: ม.4 กำหนด ข้อยกเว้น ที่ PDPA ไม่ใช้บังคับ

🎯 6 ข้อยกเว้นตาม ม.4:
  1. (1) เพื่อประโยชน์ ส่วนตัว หรือ กิจการครอบครัว
  2. (2) หน่วยงานของรัฐ ความมั่นคง + ป้องกันและปราบปรามการฟอกเงิน + ความปลอดภัยของรัฐ
  3. (3) บุคคล/นิติบุคคลที่ใช้/เปิดเผยเพื่อ กิจกรรมสื่อมวลชน · ศิลปกรรม · วรรณกรรม ตาม จริยธรรมสื่อ หรือเพื่อ สาธารณประโยชน์
  4. (4) สภาผู้แทนราษฎร · วุฒิสภา · รัฐสภา + คณะกรรมาธิการ
  5. (5) การพิจารณาคดีของ ศาล และเจ้าหน้าที่ในกระบวนการยุติธรรม
  6. (6) ข้อมูลของ บริษัทข้อมูลเครดิต (Credit Bureau) และสมาชิก ตามกฎหมายเฉพาะ
⚠️ แม้ได้ยกเว้นจาก PDPA แต่ยังต้องมี มาตรการรักษาความมั่นคงปลอดภัย ตาม ม.4 วรรค 2

🚨 Trap Cards:
  • ม.4 = ข้อยกเว้นโดยทั้งหมด (PDPA ไม่ใช้)
  • ม.5 = ขอบเขตการใช้บังคับ
  • ม.4 ≠ ม.24 (ฐานทางกฎหมาย)
  • "กิจการส่วนตัว" = ใช้บันทึกในมือถือส่วนตัว ไม่ใช่ในนามบริษัท

1️⃣2️⃣ มาตรา 40 PDPA — Processor + DPA — ออก 2 ข้อ

📚 หลัก: Processor มีหน้าที่ตามคำสั่ง Controller + ต้องมี DPA (Data Processing Agreement)

🎯 หน้าที่ Processor (ม.40):
  1. ดำเนินการ ตามคำสั่ง Controller เท่านั้น (เว้นแต่ขัดกฎหมาย)
  2. จัดให้มี มาตรการรักษาความมั่นคงปลอดภัย (ตาม ม.37(1))
  3. แจ้ง Controller เมื่อพบเหตุละเมิด โดยไม่ชักช้า
  4. จัดทำ RoPA เฉพาะส่วนของ Processor
🎯 DPA (ม.40 วรรค 3) — ต้องมีอย่างน้อย:
  1. ขอบเขต / ระยะเวลา / ลักษณะ + วัตถุประสงค์การประมวลผล
  2. ประเภท + ปริมาณข้อมูล
  3. หน้าที่ + ความรับผิดของ Processor
  4. มาตรการ ความปลอดภัย
  5. การใช้ Sub-processor (ต้องได้รับอนุญาตจาก Controller)
  6. การ คืน/ลบ ข้อมูลเมื่อสิ้นสุดสัญญา
  7. การ ตรวจสอบ (Audit) ของ Controller
  8. การช่วย Controller ตอบ DSR
🎯 กรณีที่ต้องทำ DPA:
  • จ้าง ผู้พัฒนาระบบ ที่เข้าถึงข้อมูล
  • ใช้ Cloud Service (AWS, GCP, Azure)
  • จ้างทำ Payroll / Call Center / IT Support
  • ส่ง Marketing ผ่าน Vendor
🚨 Trap Cards:
  • ตัวอย่างกรรมการ #1 → "จ้างผู้พัฒนาระบบ" = ต้องมี DPA
  • "พนักงานภายใน" ≠ Processor → ไม่ต้องมี DPA (เป็น HR Policy)
  • "คู่ค้าธุรกิจที่เป็น Controller ของตัวเอง" = ไม่ใช่ DPA (เป็น Joint Controllers หรือแยก Controller)
  • Sub-processor ต้อง ได้รับอนุญาต Controller ก่อน
  • หาก Processor ใช้ข้อมูลนอกขอบเขต → กลายเป็น Controller ทันที

1️⃣3️⃣ มาตรา 41 PDPA — DPO Appointment — ออก 1 ข้อ

📚 หลัก: Controller / Processor ต้องตั้ง DPO ใน 3 กรณี

🎯 ม.41 วรรค 1 — เกณฑ์ตั้ง DPO:
  1. (1) เป็น หน่วยงานของรัฐ ที่ PDPC ประกาศกำหนด
  2. (2) กิจกรรมหลัก = การประมวลผลข้อมูลที่ต้อง ตรวจสอบอย่างสม่ำเสมอ โดยมี ปริมาณข้อมูลจำนวนมาก (Large-scale Monitoring)
  3. (3) กิจกรรมหลัก = ประมวลผล ข้อมูล Sensitive ม.26
🎯 ม.41 วรรค 2-5:
  • DPO เป็น พนักงานภายใน หรือ Outsource ก็ได้
  • กรณี เครือบริษัท ตั้ง DPO ร่วมกันได้
  • ต้องประกาศ ข้อมูลติดต่อ DPO ให้เจ้าของข้อมูล + แจ้ง PDPC
  • DPO ต้อง เข้าถึงทรัพยากร + เข้าถึงผู้บริหารระดับสูงสุด
🎯 ม.41 วรรค 6 — คุ้มครอง DPO:
  • ห้ามไล่ออก หรือลงโทษเพราะปฏิบัติหน้าที่ตาม PDPA
  • หากเลิกจ้าง → ต้องระบุเหตุที่ไม่เกี่ยวกับการทำหน้าที่
🚨 Trap Cards:
  • ตัวอย่างกรรมการ #2 → "ระบบอัตโนมัติเฉย ๆ" ≠ เกณฑ์ตั้ง DPO
  • "พนักงาน 50 คน" ≠ เกณฑ์ตั้ง DPO (ดูที่กิจกรรมหลัก ไม่ใช่ขนาด)
  • "ขายของออนไลน์" ทั่วไป ≠ เกณฑ์ตั้ง DPO (เว้นแต่ Large + Monitoring)
  • DPO ต้องเป็น อิสระ ไม่มี Conflict of Interest (CEO/CIO/HR Head ไม่ควรเป็น DPO)
  • DPO Outsource = ต้องระบุ บุคคลที่ติดต่อจริง ไม่ใช่แค่ชื่อบริษัท

1️⃣4️⃣ มาตรา 42 PDPA — หน้าที่ DPO — ออก 1 ข้อ

📚 หลัก: DPO มี 4 หน้าที่หลัก

🎯 ม.42 วรรค 1 — 4 หน้าที่:
  1. (1) ให้คำแนะนำ (Advise) — แก่ Controller / Processor / พนักงาน เกี่ยวกับการปฏิบัติตาม PDPA
  2. (2) ตรวจสอบ (Monitor) — การปฏิบัติงานของ Controller / Processor / ลูกจ้าง
  3. (3) ประสานงาน (Cooperate) — กับ สำนักงาน กคส. (PDPC) เมื่อพบปัญหา
  4. (4) รักษาความลับ (Confidentiality) — ข้อมูลส่วนบุคคลที่ดูแลในการทำหน้าที่
🎯 ม.42 วรรค 2: Controller / Processor ต้อง ไม่กลั่นแกล้ง / ไม่เลิกจ้าง DPO เพราะปฏิบัติหน้าที่

🎯 ม.42 วรรค 3: เจ้าของข้อมูล ติดต่อ DPO ในเรื่องที่เกี่ยวกับการประมวลผล + การใช้สิทธิ

🎯 หน้าที่อื่นที่ ไม่ใช่หน้าที่ DPO ตาม ม.42 (Trap):
  • RoPA (ม.39) = หน้าที่ Controller ไม่ใช่ DPO (DPO แค่ให้คำปรึกษา)
  • DPIA = ไม่บังคับใน PDPA (DPO ให้คำปรึกษาได้)
  • Breach Notification (ม.37(4)) = หน้าที่ Controller (DPO ช่วยประสาน)
  • Privacy Notice (ม.23) = หน้าที่ Controller
  • DSR Response = หน้าที่ Controller (DPO เป็น POC)
🚨 Trap Cards:
  • ตัวอย่างกรรมการ #5 → หน้าที่ DPO = "ตรวจสอบการดำเนินงาน" (ม.42(2))
  • "จัดทำ RoPA" = หน้าที่ Controller (ม.39)
  • "ทำ DPIA" = ไม่บังคับ + ไม่ใช่หน้าที่หลัก DPO
  • "จัดทำแผน Breach" = Controller (DPO ช่วย)
  • DPO = Advisor + Monitor ไม่ใช่ Decision Maker

⭐ สูตรท่องก่อนเข้าห้องสอบ (5 นาที)

📌 ตัวเลขทอง 5 ตัว:
  • 30 วัน — DSR Response (ม.30) + ขยาย 30 วัน + อุทธรณ์ กคส.
  • 72 ชั่วโมง — แจ้ง Breach (ม.37(4)) นับจาก "ทราบเหตุ"
  • 15 วัน — เกิน 72 ชม. ต้องส่งเหตุผล
  • 1-3-5 ล้าน — โทษทางปกครอง (ม.82-84)
  • 1 ปี / 1 ล้าน — โทษอาญา (ม.79)
📌 มาตราที่ออกบ่อย:
  • ม.4 ข้อยกเว้น | ม.5 ขอบเขต | ม.6 นิยาม
  • ม.19-20 Consent | ม.23 Privacy Notice | ม.24 7 ฐาน | ม.26 Sensitive 11 ประเภท
  • ม.28-29 Cross-border | ม.30-36 DSR | ม.37 หน้าที่ Controller
  • ม.39 RoPA | ม.40 Processor + DPA | ม.41 ตั้ง DPO | ม.42 4 หน้าที่ DPO
  • ม.77-78 ทางแพ่ง | ม.79-81 ทางอาญา | ม.82-87 ทางปกครอง
📌 คำลวงที่เจอบ่อย:
  • "ทุกบริษัทต้องตั้ง DPO" — ผิด (เฉพาะ 3 กรณี ม.41)
  • "พนักงาน 50 คน → ต้องตั้ง DPO" — ผิด (PDPA ไม่ใช้เกณฑ์จำนวน)
  • "DSR ต้องตอบใน 7 วัน" — ผิด (30 วัน)
  • "แจ้ง Breach ภายใน 24 ชั่วโมง" — ผิด (72 ชั่วโมง)
  • "DPO ออกคำสั่งให้ Controller ได้" — ผิด (DPO เป็น Advisor)
  • "Pre-ticked Consent ใช้ได้" — ผิด (ม.19)
  • "Anonymized = Pseudonymized" — ผิด (Anonymized = ถาวร)
  • "Compliance Audit = Technical Measure" — ผิด (Organizational)

LIA — 3 Tests (สำคัญมาก!)

  1. Purpose Test — ระบุประโยชน์โดยชอบฯ ได้หรือไม่

  • BCR (Binding Corporate Rules) — เครือกิจการ/ธุรกิจเดียวกัน
  • Appropriate Safeguards (มาตรการคุ้มครองที่เหมาะสม)

Data Transit vs Data Transfer

Transit: ส่งผ่านโดยไม่มีเจตนาให้เข้าถึง — ไม่ใช่ Transfer
Transfer: Cloud Service / Remote Access จากต่างประเทศ = ใช่ Transfer

Appropriate Safeguards (ม.29 วรรคสาม) — 3 รูปแบบ

  1. Accepted Contractual Clauses
    • (A) Ad-hoc Contractual Clauses (คู่สัญญาจัดทำเอง)
    • (B) Foreign/International Standard Clauses
      • (B.1) ASEAN MCC (Model Contractual Clauses)
      • (B.2) EU GDPR SCC (Standard Contractual Clauses)
      • (B.3) อื่น ๆ ที่อาจประกาศเพิ่ม
  2. Certification (รอประกาศเพิ่มเติม) — เกี่ยวกับ Cross-border โดยเฉพาะ
  3. Binding & Enforceable Legal Instrument ระหว่างหน่วยงานรัฐ
🎯 ความเข้าใจผิดที่บ่อย: Certification ม.29 ต้องเป็น Cross-border Certification ไม่ใช่ ISO 27001 หรือ Privacy Certification ทั่วไป

🛡️ หัวข้อ 2: PDPA, Cybersecurity & Breach

Privacy vs Information Security

  • Privacy: "ความสามารถในการปกปิดตัวเองหรือข้อมูลของตน"
  • Information Security: "ป้องกันข้อมูลและระบบจากการเข้าถึง/ใช้/เปิดเผย/รบกวน/แก้ไข/ทำลาย โดยไม่ได้รับอนุญาต"

CIA Triad (หลักการของ Information Security)

C — Confidentiality

การรักษาความลับ

I — Integrity

ความครบถ้วนและถูกต้อง

A — Availability

สภาพพร้อมใช้งาน

Simplified Attack Scenarios — 3 จุด

  3. "กลางหัวใจ" (Servers) — Vulnerabilities, DoS, Privilege escalation

📢 การแจ้งเหตุการละเมิด (Breach Notification)

โจทย์ #2: PDPC Eagle Eye ส่งหนังสือมา

🔑 Quick Tips ก่อนตอบโจทย์

  3. เห็น "Data Portability" → ม.31 (Consent + Contract เท่านั้น)
  4. เห็น "ลบ" → ม.33 + ตรวจวรรคสอง 7 ข้อยกเว้น
  5. เห็น "ระงับใช้" → ม.34
  6. เห็น "แก้ไข" → ม.36 (Opinion ไม่ได้)
  7. เห็น "ต่างประเทศ" → ม.28 (Adequate) หรือ ม.29 (BCR)

🏛️ หน่วยงานรัฐ 153K (Web App ถูก Hack)

  1. หน่วยงานรัฐมี Web App — ถูกโจมตี — ข้อมูล 200,000 รายไป Dark Web
  2. ใช้รหัสผ่านอ่อนแอ — ไม่ประเมินความเสี่ยง
  3. ไม่มี DPA กับบริษัทพัฒนาระบบ
  4. บริษัทพัฒนาไม่ได้ออกแบบ Security ตั้งแต่ต้น

🍎 Apple Deletion Request (DPC Ireland)

หลังลบ Apple ID:

  1. เก็บ past transaction เพื่อรายงานการเงิน
  2. เก็บข้อมูลตามคำสั่งศาล

🚙 Scania VIN (Case C-319/22 EU CJEU)

  1. สมาคมอู่ซ่อมอิสระฟ้อง Scania — ขอ VIN
  2. Scania อ้างว่า VIN = Personal Data

  • VIN เป็น Personal Data — เพราะเชื่อมโยงกับเจ้าของรถได้
  • แต่สำหรับอู่ซ่อมอิสระ — VIN ไม่ใช่ Personal Data หากไม่มี means เชื่อมโยง
